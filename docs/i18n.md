# Internacionalização (i18n)

> Voltar pro [README](../README.md).

A API responde em 3 idiomas: **pt-BR**, **en**, **es** (arquivos em [`i18n/`](../i18n/)).

## Cascata de resolução

A lang é resolvida na ordem (primeiro que retornar valor não-nulo vence):

1. **`preferredLanguage` do usuário autenticado** — para rotas autenticadas, o controller injeta a lang via `@CurrentUser()` e passa explicitamente pra service. O `UserLanguageResolver` (registrado no `I18nModule`) também funciona pra exception filter, mas roda como middleware antes do guard popular `req.user`, então é redundante pras rotas autenticadas.
2. Query param `?lang=pt-BR` (`QueryResolver`).
3. Header `X-Lang` (`HeaderResolver`).
4. Header `Accept-Language` (`AcceptLanguageResolver`).
5. Default global — env `DEFAULT_LANGUAGE`, fallback `en`.

## Onde a tradução acontece

- **Mensagens persistidas**: armazenadas como **chaves i18n** (ex.: `errors.order.notFound`). A tradução acontece apenas na borda HTTP. `Order.failureReason` persiste a chave + args em JSON pra interpolar `{attempts}` etc na hora de servir.
- **Validação de DTOs** (`class-validator`): `validation.json` por idioma. Limitação: pipes rodam após o guard mas antes do controller, então usam `Accept-Language` (não `preferredLanguage`).
- **Exceções de negócio** (404, 409, 422, etc.): `errors.json`. Traduzidas pelo `HttpExceptionFilter` ou via callback no service quando precisam de args.

## Exemplos

```bash
# Sem auth: usa Accept-Language
curl -H "Accept-Language: pt-BR" http://localhost:3000/rota-inexistente
# {"message":"Recurso não encontrado", ...}

# Com auth: usa preferredLanguage do usuário (independente do Accept-Language)
curl -H "Authorization: Bearer sk_live_..." http://localhost:3000/orders/inexistente
# Mensagem em pt-BR/en/es conforme o idioma cadastrado pro usuário.
```
